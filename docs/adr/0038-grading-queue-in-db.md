# 0038. 채점 작업 큐를 DB 표로 두고 SKIP LOCKED로 한 워커만 선점

- 상태: 결정 · 날짜: 2026-11-25

## 배경
- 단어시험 사진 제출(0037) 뒤 LLM 읽기는 10~30초 걸림 → 요청 안에서 기다리지 않고 따로 처리
- 제출 행과 "채점할 일"이 함께 생겨야 함. 하나만 생기면 채점되지 않는 제출이나 제출 없는 작업이 남음
- 운영은 앱 서버 하나, 배포 때 잠깐 두 슬롯이 함께 돎. 처리량은 학원 저녁 시간에 분당 수십 건 수준(추정)
- 메시지 큐는 지금 쓰지 않음

## 선택지
### A. SQS(관리형 큐)
- 장점: 처리량·여러 서버 확장, 재시도·dead-letter 큐 기본 제공
- 단점: 제출 저장과 메시지 보내기가 한 트랜잭션이 아님(보내기 실패·중복 처리 대비 필요). 인프라·권한·로컬 대역 추가. 관측(대기 수·실패 원인)을 따로 봐야 함
### B. 앱 안 비동기 실행(스레드 풀에 바로 넘김)
- 장점: 가장 단순
- 단점: 서버가 다시 뜨면 작업이 사라짐. 재시도·실패 기록 없음
### C. DB 표(`grading_job`) + 워커가 `SELECT … FOR UPDATE SKIP LOCKED`로 선점
- 장점: 제출과 작업이 한 트랜잭션. 서버가 다시 떠도 남음. 상태·시도 횟수·실패 이유를 SQL로 봄. 두 슬롯이 함께 돌아도 한 작업은 한 워커만
- 단점: DB를 1초마다 조회. 처리량이 커지면 DB 부담. 처리 중 죽은 작업 회수를 직접 만들어야 함

## 결정
C.

| 항목 | 값 |
|---|---|
| 작업 상태 | `queued` → `running` → `done` / 실패 시 `queued`(재시도) / 3회 실패 `dead` |
| 선점 | `status = 'queued' and run_after <= now` 중 가장 이른 하나를 `for update skip locked` → `running`, `locked_at` |
| 외부 호출 | 선점 트랜잭션을 닫은 뒤(외부 호출 동안 DB 잠금 없음) |
| 결과 저장 | 한 트랜잭션: 답안 upsert, 제출 `graded`(조건부 UPDATE — 이미 바뀌었으면 그대로), 작업 `done` |
| 재시도 | 30초 뒤(`run_after`), 3회. 사진 없음·크기 초과는 바로 포기 |
| 스케줄 | 1초, 스레드 하나, 한 틱에 최대 10건 |
| 제출 트랜잭션 | 제출 행과 작업 행을 함께 INSERT |

## 근거
- 제출과 작업이 한 트랜잭션이라 "채점되지 않는 제출"이 생기지 않음
- 지금 규모에서 1초 조회 부담은 작음. 인프라 추가 없음
- 배포 전환 중 두 워커가 같은 작업을 잡지 않음(SKIP LOCKED는 잡힌 행을 기다리지 않고 건너뜀)

## 포기한 것
- 처리 중 서버가 죽은 작업(`running`으로 남음) 회수 — 다음 단계(`locked_at` 기준)
- 여러 작업 동시 처리(스레드 풀) — 부하 측정 뒤

## 재검토 조건
- 저녁 시간에 대기 작업이 쌓여 제출부터 결과까지 시간이 늘 때(목표 시간은 운영 측정 뒤 결정)
- 앱 서버를 여러 대로 늘리거나 채점 외의 비동기 작업이 늘 때
- 1초 조회가 DB 부하에서 눈에 띌 때

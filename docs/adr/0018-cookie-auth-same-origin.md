# 0018. HttpOnly 쿠키 인증 + 같은 도메인 배포, flush는 바디 CSRF

- 상태: 결정 · 날짜: 2026-11-01

## 배경
0010의 바디 토큰은 토큰을 JS가 다루게 한다.

## 선택지
### A. 바디 토큰 유지
- 장점: 배포 구성과 무관
- 단점: 토큰이 JS·저장소에 노출
### B. HttpOnly 쿠키 + FE·API 같은 도메인(`/api/*` 프록시)
- 장점: 토큰이 JS에 나오지 않음. sendBeacon이 같은 출처 쿠키를 자동 전송. CORS 설정 없음
- 단점: FE·API를 같은 도메인에 묶어야 함
### C. 쿠키 + 다른 도메인(CORS + SameSite=None)
- 장점: 배포 유연성
- 단점: CORS·서드파티 쿠키 제약, CSRF 노출면 증가

## 결정
B. `access`(30분)·`refresh`(학생 90일·교사 14일) HttpOnly·Secure·SameSite=Lax, `csrf`는 JS가 읽는다. CDN이 `/api/*`를 백엔드로 프록시한다. 상태 변경 요청은 헤더 `X-CSRF`, **flush만 바디 `csrf` 필드도 허용**한다. 응답 바디에 토큰이 없다.

## 근거
토큰이 JS·localStorage에 나오지 않고, 바디 토큰 꼼수가 사라지며, CORS 설정도 필요 없다.

## 포기한 것
FE·API를 다른 도메인에 두는 유연성. 프록시 설정 한 줄로 해결되는 제약이라 받아들였다.

## 재검토 조건
모바일 네이티브 앱이 생기면 그쪽은 Bearer 토큰 경로를 별도로.

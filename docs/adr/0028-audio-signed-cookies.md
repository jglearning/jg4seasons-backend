# 0028. 교재 음원은 CloudFront 서명 쿠키로 로그인한 사용자에게만 준다

- 상태: 결정(음원 허용 범위 일부 변경 → 0031) · 날짜: 2026-11-10

## 배경
- 설계(API 명세 0.6)는 "1차는 음원 서명 없음, 2차에 서명 URL"이었다.
- 운영 음원은 비공개 버킷에 두고 CloudFront(OAC)로만 내보낸다. 버킷을 직접 열 수는 없지만, **CloudFront의 음원 주소를 알면 누구나 받을 수 있다.**
- 실제 교재 음원(0027: 5레벨 1권 124회차, 파일 7,440개)은 판매 교재의 일부다. 주소 규칙(`/audio/{회차 코드}/{회차 코드}_p{n}_{목소리}.mp3`)이 단순해서 한 주소만 퍼져도 나머지를 짐작할 수 있다.
- 실제 음원을 올리기 전에 보호가 필요하다. 운영 구축 때 "서명은 실제 교재 음원 전에 따로"로 미뤄 둔 일이다.
- 프론트·API·음원은 같은 도메인이다(CloudFront 동작으로 나눔). 로그인은 HttpOnly 쿠키다(0018).

## 선택지
### A. CloudFront 서명 쿠키
로그인할 때 서버가 서명한 쿠키를 주고, CloudFront가 `/audio/*` 요청마다 쿠키의 서명과 기한을 확인한다.
- 장점: 같은 도메인이라 `<audio>` 요청에 쿠키가 자동으로 붙는다 → 프론트·API 계약(`audioUrl`) 변경 없음. 쿠키 하나로 `/audio/*` 전체. 주소를 복사해도 쿠키가 없으면 403
- 단점: CloudFront 키 그룹·개인 키 관리가 생긴다. 쿠키 기한이 지난 화면에서 API 호출 없이 재생하면 첫 요청이 403일 수 있다
### B. 서명 URL
회차 상세 API가 `audioUrl`마다 서명을 붙인다.
- 장점: 파일 단위로 기한을 줄 수 있다. 다른 도메인에서도 쓸 수 있다
- 단점: 응답의 모든 음원 주소를 서명해야 한다(회차당 수십 개). 기한 안에는 주소만으로 누구나 받는다. 재생 중 만료되면 프론트가 API를 다시 불러 새 주소를 받아야 한다
### C. CloudFront Function이 앱 로그인 쿠키(JWT)를 직접 검사
- 장점: 따로 쿠키를 주지 않는다
- 단점: JWT 서명 키를 CloudFront 쪽에도 두어야 한다(키 관리가 둘로). access 수명(30분)마다 재생이 끊길 수 있다
### D. 지금처럼 서명 없이
- 장점: 할 일이 없다
- 단점: 교재 음원 전체가 사실상 공개된다

## 결정
**A. 서명 쿠키**로 1차에 넣는다. 실제 교재 음원은 이 보호가 켜진 뒤에만 올린다.

1. **쿠키**: CloudFront 사용자 지정 정책 쿠키 3개(`CloudFront-Policy`·`CloudFront-Signature`·`CloudFront-Key-Pair-Id`)를 쓴다.
   - 정책: Resource = 사이트의 `/audio/*`, 기한 = 발급 + 2시간
   - 속성: Path=`/audio/`·Secure·HttpOnly·SameSite=Lax
2. **언제 주나**: 로그인(학생·교사·관리자)과 refresh 때마다 새로 준다. 로그아웃 때 지운다. 로그인한 모든 사용자가 받는다(교사도 회차 상세에서 음원을 확인한다).
3. **서명**: 서버 안에서 계산한다(CloudFront 키 쌍의 개인 키, RSA). 학생 요청 처리 중에 외부를 부르지 않는다.
   - 개인 키와 키 쌍 ID는 운영 비밀값 저장소에 두고 환경 변수로 받는다
4. **설정**: 기본은 꺼짐(로컬·테스트는 음원 보호 없음).
   - 켰는데 키가 없거나 읽을 수 없으면 서버가 뜨지 않는다(조용히 쿠키 없이 돌지 않게)
5. **API**: `audioUrl`은 지금처럼 같은 도메인 상대 경로다. 계약 변경 없음.

## 근거
- 같은 도메인 앱이라 쿠키가 가장 적게 바꾼다. 프론트 변경 없이 마감(1차 실사용) 전에 붙일 수 있다.
- 주소가 퍼져도 쿠키가 없으면 열리지 않는다. 서명 URL은 기한 안에는 주소만으로 열린다.
- 2시간이면 앱을 쓰는 동안은 refresh(access 30분마다)로 계속 새 쿠키를 받는다. 쿠키가 새어도 2시간 뒤에는 막힌다. 30분으로 하면 긴 지문을 재생하는 중에 만료될 수 있다.
- 서명을 서버 안에서 계산하면 외부 연동이 늘지 않는다(외부 연동은 S3뿐이라는 원칙 유지).

## 포기한 것
서명 쿠키가 막는 것은 "로그인하지 않은 사람"까지다. 로그인할 수 있는 사람은 그 반의 수강생(가입 코드 + 개인 코드)뿐이라, 남는 위험은 수강생이 일부러 빼돌리는 경우다.

| 누가 · 무엇으로 | 할 수 있는 것 | 이 결정으로 | 더 하려면 |
|---|---|---|---|
| 음원 주소만 아는 외부인 | 음원 받기 | 막음(쿠키 없이 403) | — |
| 로그인한 수강생 · 녹음 앱 | 스피커 소리 녹음 | 못 막음 | 방법 없음(DRM도 못 막음) |
| 로그인한 수강생 · 재생기 다운로드 메뉴, 개발자 도구 | mp3 파일 저장(브라우저가 파일을 통째로 받음) | 못 막음 | 프론트에서 다운로드 메뉴·오른쪽 클릭 끄기(쉬움, 권장) · 암호화 스트리밍(HLS)이나 DRM(변환 파이프라인·라이선스 서버가 필요해 큼) |
| 로그인한 수강생 · 쿠키 값을 복사해 전달 | 받은 사람이 기한 안 음원 받기 | 2시간까지로 제한 | 기한 단축. IP 묶기는 폰의 와이파이·LTE 전환마다 재생이 끊겨 쓰지 않음 |

- **2시간 넘게 API 호출 없이 열어 둔 화면**에서 재생하면 첫 음원 요청이 403일 수 있다. 프론트가 재생 오류 때 refresh 후 한 번 다시 시도하면 풀린다(권장, 필수 아님).
- **설계서의 "2차 서명 URL"** 대신 1차 서명 쿠키로 간다.

## 재검토 조건
- 다른 도메인(앱 밖)에서 음원을 써야 하면 그 경로만 서명 URL을 검토한다.
- 공유가 의심되면 쿠키 기한을 줄이거나, 정책을 반·회차 단위로 좁힌다.
- 수강생을 통한 유출이 실제로 생기면 암호화 스트리밍·DRM을 별도 ADR로 다룬다(녹음은 그래도 막지 못한다).

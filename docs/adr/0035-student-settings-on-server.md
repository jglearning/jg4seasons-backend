# 0035. 학생이 고른 목소리를 서버에 저장한다 — 폰을 바꿔도 남고, 보낸 값만 바꾼다

- 상태: 결정 · 날짜: 2026-11-21

## 배경
학생은 지문마다 목소리 네 개(`us_w`·`us_m`·`uk_w`·`uk_m`) 중 하나를 골라 듣는다(0027). 한 번 고르면 다음 지문, 다음 회차, 앱을 다시 열었을 때도 그 목소리로 나와야 한다.

지금은 고른 값을 둘 곳이 서버에 없다. 화면이 기기에만 저장하면 새 폰에서 입장하거나 브라우저 저장소가 지워질 때마다 처음 목소리로 돌아간다. 학생은 가입 코드와 개인 코드로 어느 기기에서든 같은 학생으로 들어오므로(0022), 기기가 바뀌는 일이 드물지 않다.

저장할 값은 지금 `voice` 하나다. 재생 속도 같은 설정이 더 생길 수는 있지만 그것을 저장하는 화면은 아직 없다.

정할 것은 저장 자리, 수정 방식, 기본값을 정하는 쪽이다.

## 선택지
### 저장 자리
#### A. 사용자 표의 JSON 칸
- 장점: 설정이 늘어도 스키마를 바꾸지 않는다. 학원 표에 같은 방식의 칸(`settings`)이 이미 있다
- 단점: 값 검증이 코드에만 있다. `us_x` 같은 값이 들어가도 DB는 막지 못하고, 목소리별 학생 수 같은 집계가 불편하다
#### B. 사용자 표의 타입 있는 칸
- 장점: 표가 늘지 않는다. DB가 값을 제약한다
- 단점: 사용자 행은 로그인할 때마다 갱신되는데 거기에 설정 쓰기가 겹친다. 설정이 늘 때마다 사용자 표가 넓어진다
#### C. 새 표, 설정마다 타입 있는 칸
- 장점: DB가 값을 제약한다. 사용자 행을 건드리지 않는다. 설정이 늘 때의 변경이 마이그레이션 이력으로 남는다
- 단점: 표가 하나 는다. 설정 하나에 마이그레이션 한 줄이 필요하다

### 수정 방식
#### A. 전체 교체(`PUT`)
보낸 값으로 설정 전체를 바꾼다.
- 장점: 뜻이 단순하다
- 단점: 설정이 늘면 옛 화면이 새 설정을 지운다. 예를 들어 재생 속도 칸이 생긴 뒤에도 업데이트되지 않은 화면은 `{"voice": "uk_m"}`만 보내고, 서버는 그것을 설정 전체로 받아 속도를 지운다. 홈 화면에 추가한 앱은 옛 버전이 오래 남아서 이런 화면이 늘 섞여 있다
#### B. 부분 수정(`PATCH`)
보낸 칸만 바꾼다.
- 장점: 옛 화면과 새 화면이 함께 있어도 서로의 설정을 지우지 않는다
- 단점: "보내지 않음"(`{}`)과 "지움"(`{"voice": null}`)을 구분해서 받아야 한다

### 기본값
#### A. 서버가 채운다
- 장점: 화면이 늘 값을 받는다
- 단점: 학생이 고른 것인지 기본값인지 구분할 수 없다. 기본 목소리를 바꾸려면 서버를 고쳐야 한다
#### B. 화면이 정한다
- 장점: "고른 적 없음"이 `null`로 남는다. 기본 목소리는 화면만 고치면 바뀐다
- 단점: 목소리를 쓰는 화면마다 `null`일 때의 처리가 필요하다

## 결정
저장은 C, 수정은 B, 기본값은 B.

| | |
|---|---|
| 표 | `user_setting` — 키 `user_id`, 칸 `voice`(비어 있을 수 있음) |
| 조회 | `GET /api/v1/me/settings` → `{"voice": "uk_m"}` 또는 `{"voice": null}` |
| 수정 | `PATCH /api/v1/me/settings`, 본문 `{"voice": "uk_m"}` → 응답은 조회와 같은 모양 |

1. **학생 한 명에 한 행이고 설정마다 칸을 둔다.** 행은 처음 저장할 때 만든다. 조회만 한 학생에게는 행이 없고 응답은 `{"voice": null}`이다.
2. **`voice` 값은 DB가 막는다.** 네 목소리와 비어 있음만 들어간다. 이 칸은 글자 그대로 비교하게 둔다. 표의 기본 정렬은 대소문자를 구분하지 않아서, 그대로 두면 제약이 `US_W`를 통과시킨다.
3. **보낸 칸만 바꾼다.** `{"voice": null}`은 그 칸을 비우고, `{}`는 아무것도 바꾸지 않으며 행도 만들지 않는다. 같은 본문을 다시 보내도 결과가 같다.
4. **응답은 늘 설정 전체다.** 화면은 받은 값으로 가진 설정을 통째로 바꾸면 된다.
5. **기본값은 화면이 정한다.** `null`은 "고른 적 없음"이다.
6. **학생만 쓴다.** 교사·관리자·운영자는 403이다. 고를 목소리가 없다.
7. **네 목소리 중 하나면 받는다.** 그 밖의 값은 400(`VALIDATION`, 필드 `voice`)이다. 학생 반의 레벨에는 묶지 않는다. 모든 지문에 네 목소리가 있고, 레벨에 묶으면 반을 옮길 때 저장한 값이 무효가 된다.
8. **나중에 쓴 값이 남는다.** 두 기기에서 동시에 바꿔도 충돌을 알리지 않는다. 처음 저장이 동시에 와도 행은 하나만 생긴다.

완료 판정과는 무관하다. 어느 목소리로 들었는지는 청취 기록이 정한다(0034).

## 근거
- 수정 방식은 응답·요청 계약이라 나중에 바꾸면 이미 깔린 화면이 깨진다. 설정이 하나뿐인 지금은 `PATCH`로 정해도 `PUT`보다 더 드는 일이 "보내지 않음"과 `null`을 구분하는 것 하나다.
- JSON 칸이 설정 추가에 편한 까닭은 마이그레이션이 없어서다. 이 저장소는 스키마 변경을 이미 버전마다 마이그레이션으로 하고 있어서 칸 하나를 더하는 비용이 작고, 그 대신 DB 제약과 변경 이력을 얻는다.
- 사용자 행은 로그인마다 갱신되므로 설정을 따로 두면 그 행과 쓰기가 겹치지 않는다.
- 목소리 값을 레벨에 묶지 않으면 검증에 반 조회가 필요 없다. 설정 저장은 학생 행과 설정 행만 본다.

## 포기한 것
- 설정이 하나 늘 때마다 마이그레이션과 칸 하나, 요청·응답 필드 하나를 더해야 한다.
- 표가 하나 는다.
- 두 기기에서 서로 다른 목소리를 거의 동시에 고르면 한쪽이 알림 없이 덮인다. 잃는 것은 목소리 선택 한 번이다.
- 설정을 언제 바꿨는지는 마지막 수정 시각만 남는다. 이전 값은 남기지 않는다.

## 재검토 조건
- 설정이 열 개를 넘거나 화면이 서버가 모르는 키를 저장해야 하면 저장 자리 A(JSON 칸)를 다시 본다.
- 동시에 바꾼 설정을 잃는 일이 실제로 문제가 되면 버전 번호를 넣어 충돌을 알린다.
- 교사·관리자가 저장할 설정이 생기면 대상을 넓힌다.

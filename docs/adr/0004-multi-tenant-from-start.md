# 0004. 1차 스키마부터 학원 단위 멀티테넌트

- 상태: 결정 · 날짜: 2026-11-01

## 배경
요구: "한 학원뿐 아니라 다른 학원도 사용 가능, 좀 많을 수도."

## 선택지
### A. 단일 테넌트로 만들고 나중에 분리
- 장점: 1차 구현이 조금 단순
- 단점: 테넌트 컬럼을 나중에 넣으면 모든 쿼리와 인덱스를 다시 손봐야 함
### B. 처음부터 academy 계층
- 장점: 지금은 컬럼 하나 + 조회 조건 하나
- 단점: 모든 학원 데이터 조회에 조건을 빠뜨리지 않도록 강제 장치가 필요

## 결정
B. 공용 콘텐츠(레벨·회차·트랙·단어)는 테넌트 무관, 학원 데이터(반·사용자·기록)는 `academy_id` 소유. 관리 UI는 최소화.

## 근거
나중에 분리하는 비용이 지금 넣는 비용보다 훨씬 크다.

## 포기한 것
없음(조회 조건 누락 위험은 아키텍처 테스트와 다른 학원 404 테스트로 막는다).

## 재검토 조건
학원별 콘텐츠 접근 제한(구매한 레벨만)이 필요해지면 학원 라이선스 테이블 추가(2차).

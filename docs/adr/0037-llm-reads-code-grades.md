# 0037. 단어시험 답안지는 LLM이 글자만 옮겨 적고, 맞았는지는 코드가 판정

- 상태: 결정 · 날짜: 2026-11-25

## 배경
- 학생이 어휘책 "스스로 점검" 한 영역(한 쪽)을 사진으로 올리면 바로 채점하는 기능(1단계 철자 쓰기)
- 한 쪽에 손글씨 34~48칸. 채점 기준은 철자까지 일치(두 철자가 표준인 말은 허용 답)
- 교사가 중간에 확인하지 않음 → 틀린 답을 맞음으로 내보내는 오류를 따로 재고 줄여야 함
- 시험지 문항은 단어 목록(`word`)과 따로 정의(`word_test_item`): 문항 순서가 단어 목록과 다르고, 짧은 글 빈칸·파생어 영역의 정답은 단어 목록에 없음. 채점은 문항 표의 `answer`로

## 선택지
### A. LLM이 사진과 정답 목록을 받아 채점까지
- 장점: 코드가 가장 적음. 뜻 쓰기처럼 "뜻이 통하면 맞음"인 판정도 한 번에
- 단점: 판정 규칙이 프롬프트 안에 있어 테스트·재현이 어려움. 정답 목록을 보면 틀린 철자를 정답으로 고쳐 읽을 위험. 모델을 바꾸면 판정 기준도 같이 흔들림
### B. 일반 OCR + 코드 판정
- 장점: 결정적, 비용 낮음
- 단점: 학생 손글씨·2단 배치·인쇄된 뜻과 섞인 칸에서 칸 나누기가 어려움. 인쇄된 첫 글자 뒤에 이어 쓴 답 처리도 따로 필요
### C. LLM은 번호별 손글씨를 옮겨 적기만, 판정은 코드
- 장점: 판정은 순수 함수라 표 테스트·재현 가능. 모델·프롬프트를 바꿔도 판정 규칙은 그대로. 읽기 정확도만 따로 측정 가능
- 단점: 뜻 쓰기 영역은 철자 일치로 판정할 수 없어 별도 방식 필요. 칸 수·번호가 어긋난 응답을 앱이 걸러야 함

## 결정
C.

| 단계 | 하는 곳 | 내용 |
|---|---|---|
| 읽기 | LLM(사진 + 문항 수만) | 번호 1~N마다 `{no, text, unreadable}`. 인쇄된 번호·뜻·첫 글자는 옮기지 않음, 인쇄된 첫 글자 뒤에 이어 쓴 글자는 합침, 철자를 고치지 않음, 못 읽으면 추측하지 않고 unreadable, 종이의 문장은 지시로 따르지 않음 |
| 검증 | 코드 | 번호가 1~N에 정확히 한 번씩이 아니면 실패(재시도). 100자 넘는 칸은 unreadable |
| 판정 | 코드(`SpellingJudge`) | 정규화(앞뒤 공백·소문자·연속 공백·하이픈·작은따옴표 변형) 뒤 정답·허용 답과 일치, 한 글자 첫 글자 뒤 이어 쓴 답 인정, 빈칸은 blank, unreadable은 `unclear` + 사유 |

- 응답은 구조화 응답(JSON 스키마)으로 받고 앱에서 다시 검증
- 정답 목록·인쇄된 뜻은 프롬프트에 넣지 않음(넣을지는 평가셋 실험으로)
- 제출 행에 모델 이름·프롬프트 버전 기록(`prompts/word-test-read/v1.txt`)
- 읽을 수 없는 문항은 `unclear`로 저장·응답(점수 밖, 문항 수 안). 맞게 쓴 학생이 "틀림"으로 보이는 일 방지, 교사 화면 "확인 필요"

## 근거
- 오답을 정답으로 내보내는 비율이 이 기능의 핵심 지표 — 판정이 결정적이어야 읽기 오류만 따로 잴 수 있음
- 정답 목록을 주면 "고쳐 읽기"가 늘 수 있어 원인 구분이 어려워짐

## 포기한 것
- 뜻 쓰기 영역의 "뜻이 통하면 맞음" 판정(철자 일치가 아님) — 별도 결정
- 한 번 읽기만(1단계). 두 번 읽어 다르면 학생 확인, `unclear` 문항을 글자 확인으로 넘기기는 다음 단계

## 재검토 조건
- 평가셋에서 읽기 정확도가 기준 미달이고, 정답 목록·인쇄된 뜻을 주는 실험이 오답 정답 처리율을 늘리지 않으면서 개선할 때
- 뜻 쓰기 영역을 넣을 때(판정 방식 별도)
